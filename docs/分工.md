# 分工表

## 體驗流程

**寄放抱怨 → 抱怨專輯（饒舌主打歌＋封面）→ 敲木魚 → 功德圓滿，分享到社群**

1. **寄放**：選情境或自由輸入，「今天受的氣，先寄放這裡。」
2. **抱怨專輯**：嘴替一句話、專輯封面（梗圖＋判詞當專輯名）、30 秒饒舌主打歌與歌詞。
3. **敲木魚**：敲滿 10 下，把怨氣敲散。
4. **功德圓滿**：勾選今天照顧自己的事，產生分享圖，可以下載或分享到 IG、LINE。

**原則**：全部在瀏覽器裡完成，使用者的抱怨不上傳。功德不等於忍耐。

## 四個角色

| 角色 | 分支 | 負責人 | 主要負責的檔案 |
| --- | --- | --- | --- |
| A 文案與梗圖 | `feature/memes-humor` | （填名字） | `js/content.js`、`assets/memes/` |
| B 饒舌與音樂 | `feature/rap-mode` | （填名字） | `js/rap.js`、`css/rap.css`、`assets/music/album/` |
| C 視覺與分享 | `feature/visual-share` | （填名字） | `js/album.js`、`js/merit.js`、`css/style.css` |
| D 統整與測試 | `feature/flow-test` | （填名字） | `index.html`、`js/app.js`、`docs/`，以及管理 `main` |

## 協作規則

- **小步合併**：每個人每週至少開一次 Pull Request，一個 PR 只放一件事。
- **合併日**：每週固定一天（例如週四），D 把大家的 PR 合進 `main`，全組一起把流程走一遍，約 15 分鐘。
- **`main` 隨時能跑**：只有 D 按 Merge。開 PR 前先把最新的 `main` 合進自己的分支，確認沒壞。
- **改共用的東西先講**：情境 id、判詞長度、`drawCover()` 的參數，別人都在用，要改先在群組或 PR 裡標註受影響的人。
- **用佔位內容先接起來**：梗圖、歌還沒到時畫面會顯示「待補」，不用互相等。

## A 文案與梗圖｜feature/memes-humor

- [ ] 每個情境的 `roast`（嘴替）各寫 3～5 句候選，挑最好笑的
- [ ] 判詞 `verdict` 會當成專輯名：短、有梗、像宮廟公文（建議 14 字以內）
- [ ] 迴向 `blessing` 會印在分享圖上，一兩行內寫完
- [ ] 五個情境＋「其他」各做一張梗圖，依檔名放進 `assets/memes/`（`guess.png`、`revise.png`、`rush.png`、`firefight.png`、`leave.png`、`other.png`）
  - 要能當 1:1 封面，畫面中央留空間放專輯名
  - 寬度 1080px、單張 500KB 以內
- [ ] 新增情境（例如：會議開不完、功勞被搶、績效面談）時，通知 B 補歌詞與主打歌
- [ ] 只用自製或有授權的圖，來源記在 `assets/memes/CREDITS.md`
- 地獄梗的界線：酸情境、不酸人；不拿死亡、疾病、身心障礙、性別、族群開玩笑；**不把忍耐包裝成美德**

## B 饒舌與音樂｜feature/rap-mode

- [ ] 改寫 `RAP_VERSES` 裡每個情境的四句歌詞（現在是草稿），押韻、有節奏感
- [ ] 用 AI 音樂工具替每個情境做一首 30 秒的歌，放 `assets/music/album/<情境id>.mp3`
  - 選工具前先看授權條款，記下工具名稱、方案與生成日期，寫在 `assets/music/CREDITS.md`
  - 歌詞用 `RAP_VERSES` 的版本，讓網頁字幕和歌對得上
- [ ] `startRap()`：歌詞跟著音樂一行一行亮起來，像卡拉 OK 字幕
- [ ] 進階：用瀏覽器的語音朗讀（Web Speech API，選 zh-TW 聲音）把使用者輸入的關鍵字念在 beat 上，錄成自己的版本；不上傳任何內容
- 歌詞一樣遵守地獄梗的界線

## C 視覺與分享｜feature/visual-share

- [ ] 專輯封面 `drawCover()`：字體、排版、專輯感細節（曲目編號、條碼、警示標籤風格的小標）
- [ ] 沒有梗圖時的預設封面，每個情境不同配色
- [ ] 專輯頁版面與進場動畫（例如黑膠從封套滑出）
- [ ] 木魚：敲擊音效、功德圓滿動畫（金光、煙霧）
- [ ] 分享圖 `drawShareCard()`：印章、迴向、今日功德的排版；另做 IG 限動尺寸（1080×1920）
- [ ] 整體樣式與手機版檢查
- 工作量較大，木魚的部分可以請 D 支援

## D 統整與測試｜feature/flow-test

- [ ] 管理 `main`：審 PR、合併、合併後把整個流程走一遍
- [ ] 主持每週合併日，更新這份分工表的進度
- [ ] 負責共用檔案 `index.html`、`app.js`；其他人需要改時由 D 協調
- [ ] 分享功能實測：手機上的 IG、LINE、Threads，以及電腦上的下載
- [ ] 規劃並執行使用者測試（Design Thinking 的「測試」階段），回饋記在 `docs/`
  - 文案是否被理解、梗圖與饒舌是否好笑或冒犯、敲木魚的次數是否剛好、是否願意分享
- [ ] 準備成果展示（Demo 流程、簡報）
